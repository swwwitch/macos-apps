# リリース作業チェックリスト

ソースの公開、署名・公証、実機確認、配布、記事の公開を別々に記録する。未実施を完了にしない。

1. ソースを確定する
   - GitHubをfetchし、未コミット変更を保全して統合する。
   - バージョン・build番号を確認する。別Macの配布済みbuildより番号を戻さない。
   - READMEと更新履歴を更新し、機能・修正内容を説明する。
2. 検証する
   - 対象アプリの自動テスト、ローカライズ、コンパイルを確認する。
   - 変更機能、設定保持、起動・再表示・終了を実機で確認する。
3. 公証ビルドを作成する
   - Developer ID Application証明書と秘密鍵を確認する。無い場合は別の署名で代替しない。
   - NO_DEPLOY=1でビルドし、Hardened Runtime・タイムスタンプ付きで内側から署名する。
   - 公証のAcceptedを確認し、チケットを添付する。署名・stapler・Gatekeeperを検証する。
4. DMGを作成する
   - 検証済みアプリから作成し、読み取り専用で開いて内部の名前・version・buildを確認する。
   - 内包アプリの署名と公証チケット、DMGの整合性を確認する。
5. 配布する
   - 既存版を保全し、実行中の処理を守って/ApplicationsとDropboxのLatest Buildsへ配置する。
   - 2か所のBundle ID・version・build・署名・内容一致と/Applications版の起動を確認する。
   - DMGはNotarized DMGs/Latestに各アプリ1本。旧版はArchive/アプリ名へ移す。
   - README、SHA256SUMS、移動・検証記録を更新する。同名の異なる内容は上書きしない。
6. GitHubを更新する
   - ソースと更新履歴をcommit・pushし、リモートHEADを照合する。
   - 個別アプリのリポジトリは既存の公開構成と履歴を保持して同期する。
   - 検証済みDMGを添付したReleaseを作成し、タグ・版・更新履歴・ダウンロードを確認する。
   - バイナリ未完成の場合はリリース済みと記載せず、既存の配布物を保持する。
7. GitHub Projectsを更新する
   - 対象Projectと既存項目を確認し、変更概要・版・検証結果・未完了理由・Releaseへのリンクを更新する。
   - 配布・記事更新まで完了してから完了状態にする。既存項目を重複作成しない。
8. note記事を更新する
   - 既存記事の本文・更新履歴・DMG添付・GitHubリンクを更新する。
   - 見出し画像は共通テンプレート、既存ハッシュタグは保持して必要なものを追加する。
   - 公開後に本文・添付ファイル・タグ・リンクを読み戻す。ダウンロードしたDMGの版とハッシュを確認する。
9. 完了記録を残す
   - ソースコミット、build、公証結果、配置先、GitHub Release、Projects、note記事を対応付ける。
   - 成功・未実施・ブロック中を分け、復元用バックアップの場所を記録する。

## 成果物を特定する必須記録

対象SHA・版・build・SHA-256・署名・公証結果をセットで記録する。.appには相対パス・権限・通常ファイルのSHA-256・リンク先を記録したマニフェスト、DMGと配布アーカイブにはファイル自体のSHA-256を付ける。名前だけで一致と判断しない。同名異内容の成果物は上書きせず履歴を保全して別名で識別する。担当変更・引き継ぎ・再開時にもこの組を照合する。
